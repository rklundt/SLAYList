# Sprint 1.6 — IaC capture in Bicep (Phase B walkthrough)

This guide drives the operator through the human-executed half of Sprint 1.6: install Bicep, deploy the captured templates to a throwaway resource group, compare against live dev, and tear down. The end state proves the Bicep faithfully re-creates the Epic 1 landing zone — which is what makes Sprint 9.1 (prod) a parameter substitution instead of a portal-walkthrough repeat.

**Time budget:** ~30–45 min, mostly waiting on deploys. Throwaway RG cost: <$0.10 (resources exist for ~10 min).

**Prerequisites:** logged into `az` with the same account that owns the dev subscription. The throwaway deploy must land in the same subscription so subscription-scoped role definitions resolve.

## D39 in one sentence

We chose Bicep over ARM JSON / Terraform / portal-export-only, and we validate by deploy-to-throwaway-RG rather than by portal-export-round-trip. The full reasoning is in `docs/DECISIONS.md` D39.

## Steps

### 0. Install Bicep CLI locally

If `az` already has Bicep installed, skip. Otherwise:

```
az bicep install
az bicep version
```

The expected version is `0.43.x` or newer. Older versions may not parse the API versions used by the templates (CAE workload profiles, EG system topic MI).

### 1. Pick parameter values

Pull these from the gitignored `infra/dev-resources.md`:

- `notificationEmail` — the same address that receives dev budget alerts today (placeholder in committed files; real value in gitignored notes).

Pick these fresh for the throwaway deploy (do NOT reuse dev's values):

- `env` = `validate` (intentionally not `dev` so the throwaway RG and its resources can never collide with live dev names)
- `region` = `use2`
- `workload` = same workload slug as dev (so the naming pattern is exercised faithfully)
- `app` = same app slug as dev

The naming module's storage-account length-aware fallback will automatically drop the workload segment if `validate` pushes the name over 24 chars. That's intentional — it's the same drop-rule prod will hit if it ever needs to.

### 2. Create the throwaway resource group

```
az group create \
  --name rg-<workload>-<app>-validate-use2 \
  --location eastus2 \
  --tags workload=<workload> app=<app> env=validate region=use2 managed-by=bicep
```

### 3. Deploy

```
az deployment group create \
  --resource-group rg-<workload>-<app>-validate-use2 \
  --template-file infra/bicep/dev/main.bicep \
  --parameters \
      env=validate \
      region=use2 \
      workload=<workload> \
      app=<app> \
      notificationEmail=<your-email>
```

Expected: ~3–5 min. The deployment provisions LAW, App Insights, budget, SWA Free, storage account + 3 containers + Songs table + 2 queues + 3 diagnostic settings, Container App Environment + Container App + system-assigned MI + 2 RBAC role assignments scoped to the storage account, Event Grid system topic + MI + diagnostic setting.

If it fails partway through: read the error (`az deployment group show -g <rg> -n main` then drill into the `properties.error.details`), fix the Bicep, redeploy. Do NOT proceed to comparison until a clean deploy is on record.

### 4. Compare against live dev

```
az resource list -g rg-<workload>-<app>-dev-use2 \
  --query "[].{type:type,name:name}" -o tsv | sort > /tmp/dev.txt

az resource list -g rg-<workload>-<app>-validate-use2 \
  --query "[].{type:type,name:name}" -o tsv | sort > /tmp/validate.txt

diff /tmp/dev.txt /tmp/validate.txt
```

Expected output: a small diff that boils down to *name differences only* (`dev` vs `validate` in every resource name) — NO type-level differences. Resource counts should match exactly.

**If there is a type-level diff** (a resource present in dev but not in validate, or vice versa), the Bicep is missing something. Fix it, redeploy to validate, re-diff. Do not advance.

**Known-acceptable additions in dev** that should NOT appear as missing in validate:
- Sprint 7.1's Event Grid subscription (deliberately deferred — neither RG has it; if dev does, dev got it from a manual portal click that needs to be captured in Sprint 7.1's IaC delta).
- Sprint 6.1's real transcoder image revisions (the validate Container App runs the placeholder image; dev may run a different image once Sprint 6.1 lands).
- Resource Group itself (not in `az resource list`, but worth confirming both RGs exist with the same tags).

### 5. Spot-check three properties beyond resource counts

`az resource list` only shows types and names. Three properties are load-bearing and not in that list — spot-check them in the portal or via targeted CLI:

a. **SWA `repositoryUrl` is empty.** Per D22 safeguard from Sprint 1.2. The validate SWA should match.

   ```
   az staticwebapp show -n swa-<app>-validate-use2 -g rg-<workload>-<app>-validate-use2 \
     --query "{repo:repositoryUrl, provider:provider}"
   ```

   Expected: `repositoryUrl: null` (or empty), `provider: None`.

b. **Container App has system-assigned MI and two role assignments.**

   ```
   az containerapp show -n ca-<workload>-<app>-validate-use2 -g rg-<workload>-<app>-validate-use2 \
     --query "identity.{type:type, principalId:principalId}"
   ```

   Expected: `type: SystemAssigned`, a non-null `principalId`. Then:

   ```
   az role assignment list --assignee <principalId> --all -o table
   ```

   Expected: at least two rows — Storage Blob Data Contributor and Storage Queue Data Message Processor, both scoped to the validate storage account.

c. **Storage account has soft-delete + versioning on.**

   ```
   az storage account blob-service-properties show \
     --account-name <validateStorageName> \
     --query "{soft:deleteRetentionPolicy.enabled, ver:isVersioningEnabled}"
   ```

   Expected: both `true`.

### 6. Attest in gitignored notes

In `infra/dev-resources.md` (gitignored), under a new `## Sprint 1.6 — IaC validation attestation` section, record:

- Date of validation
- Bicep CLI version used
- Whether the resource-list diff was clean (yes/no — if no, what differed and how it was reconciled)
- Whether all three spot-checks (5a/5b/5c) passed
- Any known-limitation properties that the Bicep can't capture (record them so Sprint 9.1's operator knows what to portal-tweak post-deploy on prod)

This is the human attestation that closes Sprint 1.6's main acceptance bullet.

### 7. Tear down the throwaway RG

```
az group delete --name rg-<workload>-<app>-validate-use2 --yes --no-wait
```

The `--no-wait` is fine — the RG goes away on its own in a few minutes. Confirm later with `az group exists -n rg-<workload>-<app>-validate-use2`.

**Important:** delete the *RG*, not individual resources. The RG delete cascades and is the only way to be sure nothing lingers (especially diagnostic settings and role assignments, which are easy to miss when deleting piecemeal).

## What this sprint does NOT do

- **No subscription-scope deploys.** The Bicep is RG-scoped; create the RG manually first. This matches how dev was hand-built and keeps the throwaway deploy from needing subscription-scope role privileges.
- **No prod deploy.** Sprint 9.1 is where prod gets stood up via the same Bicep with `env=prod`. Sprint 1.6 only proves the templates work.
- **No Event Grid subscription.** Per Sprint 1.5 deferral, the subscription + the EG system topic MI's role assignment on the work queue land in Sprint 7.1 alongside the real consumer.
- **No GitHub Actions integration.** Running these templates from a workflow lands when there's a real reason to (e.g. prod redeploy automation in Sprint 9.x). For now, this is operator-from-laptop work.

## Step 8 (recommended) — `what-if` against the live dev RG

The throwaway-RG pass proves the templates *create* a faithful copy from nothing. It does NOT prove the templates are safe to run against an environment that already has state. For that, use ARM's dry-run engine, which changes nothing:

```
az deployment group what-if \
  --resource-group rg-music-slaylist-dev-use2 \
  --template-file infra/bicep/dev/main.bicep \
  --parameters env=dev region=use2 workload=music app=slaylist \
      notificationEmail=<your-email> budgetStartDate=2026-05-01
```

Pass `budgetStartDate=<dev's actual budget start, first-of-month>` — the budget `startDate` is immutable once set, so omitting it (and letting the default compute the current month) produces a false "modify" diff or an error.

**How to read the output** (see D39 "Known what-if interpretation notes" for the full list):
- **Expected and safe:** `tags.managed-by: manual→bicep` and `tags.region: →use2` on every resource (the whole point of moving to IaC).
- **Spurious deletes you should ignore:** `stableInboundIP`, `trafficSplitting`, `runningStatus`, `maxInactiveRevisions`, container `defaultEncryptionScope`, blob `allowPermanentDelete`, CAE `peerAuthentication`, classic queue `logging`. These are computed/read-only/default-applied fields ARM won't actually change.
- **Unevaluated diffs you should verify by hand, not trust blindly:** diagnostic-setting `logs`/`metrics` arrays, the Container App `containers` array, CAE `customerId`. what-if punts on these; confirm them equal to dev with a direct `az ... show` query.
- **The one genuinely informative line:** two `Create` entries for role assignments. On a fresh prod deploy that's correct. **On a dev reconcile it means trouble** — see below.

If anything shows up that ISN'T on those lists — especially a `Delete` or `Modify` on a *data* property (retention days, versioning, SKU, network access) — STOP. That's a real capture gap; fix the Bicep before going further.

## Reconciling the live dev RG to the Bicep (optional, deliberate, not part of core Sprint 1.6)

Running `az deployment group create` (not what-if) against `rg-music-slaylist-dev-use2` would make dev's tags say `managed-by=bicep` and bring dev fully under IaC. It is **safe on the data plane** (the what-if confirms no retention/versioning/SKU changes), but two caveats apply specifically to reconciling an *existing* environment:

1. **Role-assignment 409.** The Bicep names role assignments deterministically; dev's two existing assignments (Sprint 1.4, portal-created) carry random GUIDs. Azure rejects a duplicate principal+role+scope even under a new name, so the deploy would fail with `RoleAssignmentExists`. To reconcile, first delete dev's two existing assignments (`az role assignment delete --assignee <CA-MI-principalId> --scope <storage-id>`), then deploy — the Bicep recreates them with deterministic names. There's a brief RBAC gap, harmless on a scale-to-zero placeholder.
2. **Budget endDate clears + 33% action-group decouples.** The dev budget's 5-year `endDate` would be removed (a no-end budget runs indefinitely — fine) and the auto-attached "Application Insights Smart Detection" action group would be removed from the 33% rung (alerts still email; this is the accepted action-group divergence). Neither affects alerting behavior.

**None of these apply to the fresh prod build (Sprint 9.1)** — prod starts empty, so the role assignments create cleanly and there's no pre-existing budget to reconcile. Reconciling dev is a nice-to-have for tidiness, not a prerequisite for anything.

## If something goes wrong

- **Deployment fails on a quota/policy issue.** That likely reflects a real subscription-level constraint that would also bite prod. Capture the error in the gitignored notes and treat it as a finding — do not work around it by removing the offending resource from the Bicep.
- **Comparison shows the validate deploy is missing a resource.** The Bicep is wrong; fix it, redeploy, re-diff.
- **Comparison shows dev is missing a resource that validate has.** Unlikely, but means the Bicep added something dev doesn't have — investigate; either the Bicep over-reaches (remove it) or dev is missing something that should be there (add to dev manually, OR redeploy the Bicep to dev once we're confident — operator's call).
- **Throwaway RG won't delete.** Usually a soft-deleted resource holding a lock. Check `az resource list -g <rg>` for residue; manually delete any leftover diagnostic settings or role assignments scoped to resources outside the RG.
