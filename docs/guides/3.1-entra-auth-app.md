# User-auth Entra app + three roles — operator guide (Sprint 3.1)

Creates the custom Entra **app registration** the Static Web App will use as its login provider (Epic 3), and defines the three app roles (`listener` / `uploader` / `admin`). Provisioned by a committed, idempotent **bootstrap script** rather than portal clicks — same rationale as the deploy identity (D41): a Graph object, not ARM, so it's a reviewed script, not Bicep and not manual.

> **What this sprint does and doesn't:** 3.1 creates the app registration + the role *definitions* only. It does **not** assign anyone a role (that's Sprint 3.2), does **not** wire the SWA login flow or swap the D22 gate (Sprint 3.3), and does **not** create a client secret or redirect URI (also 3.3). It changes nothing about the currently-deployed app — the Epic 2 gate stays exactly as it is until 3.3.

## The one-liner

From the repo root (PowerShell):

```
powershell -ExecutionPolicy Bypass -File .\scripts\bootstrap-auth-app.ps1
```

That's the whole setup for dev. Flags (self-documenting — `Get-Help .\scripts\bootstrap-auth-app.ps1 -Full`):

- `-DryRun` — print every create/set without doing it. **Run this first.**
- `-RunUpToStep N` — run only steps 1..N then stop (cautious, incremental).
- `-Env prod` — the prod bootstrap (Epic 9): a **separate** `slaylist-auth-prod` app registration (D7).

**Prerequisites:** `az login` to the tenant that will own the app (the same tenant as your Azure subscription). Creating an app registration + service principal requires directory permission — **Application Administrator** or **Cloud Application Administrator**, or a **personal tenant** where you are the owner (most family setups). No `gh` needed (this script touches Entra only, not GitHub).

If PowerShell's execution policy blocks it, prefix with `powershell -ExecutionPolicy Bypass -File …` (above) or set it once: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

## What each step is (and the manual Azure-portal equivalent)

Each is check-then-create / declarative-set (idempotent). Portal equivalents if you'd rather see it by hand:

**1. App registration** — the identity the SWA logs users in against.
- *Portal:* Microsoft Entra ID → App registrations → New registration → name `slaylist-auth-dev` → **Supported account types: "Accounts in this organizational directory only"** (single tenant) → Register.

**2. App roles** — the three roles that ride in the user's token. The `value` strings (`listener`/`uploader`/`admin`) must match `shared/src/types.ts` `ROLES` exactly; the role IDs are fixed in the script so re-runs never break Sprint 3.2's assignments.
- *Portal:* the app → **App roles** → Create app role, three times. For each: Display name, **Allowed member types = Users/Groups**, **Value** = `listener` / `uploader` / `admin`, a description, Enabled. (D20: a single library-scoped `admin` — do **not** add a platform/global admin.)

**3. Service principal** — the registration's account in this tenant (an **Enterprise Application**). Role *assignment* (Sprint 3.2) and the SWA auth flow both need it. The portal auto-creates it when you register via UI; the CLI doesn't (so it's a separate `az ad sp create`).

**4. Require user assignment** — only users an admin has assigned a role can sign in. **This is the mechanism that closes Epic 2's any-Microsoft-account gap.** No users are assigned yet (Sprint 3.2 does that), so until then nobody can complete sign-in — expected, and harmless because the gate isn't pointed at this provider until 3.3.
- *Portal:* Enterprise applications → `slaylist-auth-dev` → Properties → **Assignment required? = Yes** → Save.

## Capture + attest

The script ends by printing the **appId** and **tenantId**. Record them in gitignored `infra/dev-resources.md` (the "User-auth app registration" section of the template) — **never in a committed file** (D17). Sprint 3.3 reads them to wire the SWA custom provider.

Verify (the script prints these for you):
- `az ad app show --id <appId> --query "appRoles[].value"` → exactly `admin`, `listener`, `uploader`.
- `az ad sp show --id <appId> --query "appRoleAssignmentRequired"` → `true`.
- Re-run the script once → every step reports "exists / already required" (idempotency confirmed).

## After this

- **Sprint 3.2** assigns a family member (a shared Model-A account) one of these roles.
- **Sprint 3.3** wires the SWA login flow to this app registration (creates the client secret as a SWA app setting + the redirect URI), swaps the `staticwebapp.config.json` gate's redirect from `/.auth/login/aad` to the custom provider, and has the API read the role from the token. That's when the any-Microsoft-account gap actually closes on the deployed site.
- **Epic 9** re-runs this script with `-Env prod` for the separate `slaylist-auth-prod` app.
