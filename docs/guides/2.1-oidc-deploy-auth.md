# Sprint 2.1 — Deploy identity (OIDC) operator guide

Sets up the credential GitHub Actions uses to deploy to Azure, via **OIDC federation** — no stored secret (D30/D37/D41). Provisioned by a committed, idempotent script so it's reviewable and prod-repeatable (D41), not portal clicks. **Nothing deploys in this sprint** — this is credentials only; the workflow + the D22 auth gate come in Sprint 2.2.

## The one-liner

From the repo root (PowerShell):

```
powershell -ExecutionPolicy Bypass -File .\scripts\bootstrap-deploy-identity.ps1
```

That's the whole sprint. The script is self-documenting — run `Get-Help .\scripts\bootstrap-deploy-identity.ps1 -Full` for the big-picture/steps/why. Useful flags:

- `-DryRun` — print every create/set without doing it. **Always run this first.**
- `-RunUpToStep N` — run only steps 1..N then stop (cautious, incremental). e.g. `-RunUpToStep 3`.
- `-Env prod -Branch main -ResourceGroup rg-music-slaylist-prod-use2` — the prod bootstrap (Epic 9), which creates a **separate** `slaylist-github-deploy-prod` app (D7 two-app model).

If PowerShell's execution policy blocks it, either prefix with `powershell -ExecutionPolicy Bypass -File ...` (above) or set it once: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

## What each step is (and the manual Azure-portal equivalent)

The script does these in order; each is **check-then-create** (idempotent). If you'd rather do any by hand to understand it, here's the portal equivalent.

**1. App registration** — the *identity* GitHub Actions will act as.
- *Portal:* Microsoft Entra ID → App registrations → New registration → name `slaylist-github-deploy-dev` → Register.
- Note: the portal auto-creates the service principal (step 2) when you register via UI; the CLI does not, which is why step 2 is separate.

**2. Service principal** — the identity's usable instance in your directory (shows as an **Enterprise Application**). Roles attach to this.
- *Portal:* no clean standalone button for a CLI-made app. It's auto-created when you assign the app a role (step 4) via a resource group's Access control (IAM). Or run just `az ad sp create --id <appId>`.

**3. Federated credential** — the OIDC trust ("Actions on this repo+branch may BE this identity"). No secret.
- *Portal:* the app registration → Certificates & secrets → **Federated credentials** tab (not Client secrets) → Add credential → scenario **"GitHub Actions deploying Azure resources"** → Organization `rklundt`, Repository `SLAYList`, Entity type `Branch`, Branch `develop` (→ subject `repo:rklundt/SLAYList:ref:refs/heads/develop`), Name `github-rklundt-SLAYList-develop` → Add.

**4. Contributor RBAC on the env resource group ONLY** (never the subscription — D30/D7).
- *Portal:* `rg-music-slaylist-dev-use2` → Access control (IAM) → Add role assignment → Contributor → Members → select `slaylist-github-deploy-dev` → Review + assign. (This also creates the service principal if it didn't exist.)
- Contributor = full create/update/delete on resources in this RG (but NOT access management). Tightening to a least-privilege custom role is a tracked backlog item.

**5–6. GitHub repo secrets** — set via `gh secret set` (values piped via stdin, never on the command line):
- `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` (stored as **secrets**, not variables — they're really identifiers, but on a public repo GitHub masks secrets in logs and not variables, so this avoids a recon breadcrumb; D30 implementation note).
- `AZURE_STORAGE_CONNECTION_STRING` (D25), `APPINSIGHTS_CONNECTION_STRING` (D24) — genuinely sensitive, fetched live from Azure.
- *Portal/UI equivalent:* repo → Settings → Secrets and variables → Actions → New repository secret, for each.
- **NOT set (D37):** the SWA deployment token — break-glass only, stays in gitignored notes.

## Verify + attest

The script ends by printing `gh variable list` (expect **empty**) and `gh secret list` (expect exactly the **5** above, **no** SWA-deploy-token secret). Record that in the gitignored `infra/dev-resources.md` "Sprint 2.1" attestation: the app/client/tenant/subscription IDs, the federated subject, the RBAC scope, and the secret list.
