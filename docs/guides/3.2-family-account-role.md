# Shared family account + role assignment — operator guide (Sprint 3.2)

Creates the **shared family Entra account** (Model A — admin-made, because the kids may not have their own email yet, per D2) and **assigns it a role** on the `slaylist-auth-dev` app registration from Sprint 3.1. This is what finally gives you an identity that can sign in once Sprint 3.3 points the gate at this provider.

> **Hygiene:** this guide uses **placeholders** for every real value (`<your-tenant>`, `<family-uploader-account>`, `<admin-account>`). Your real account names, UPNs, and the shared password go **only** in gitignored `infra/dev-resources.md` — never in a committed file (D17). Use **non-identifying** account names (no kid's real name — that's PII per D21/D32); a generic uploader/kids-style label and a generic admin label are the right shape.
>
> **What this sprint does and doesn't:** 3.2 creates accounts + assigns roles only. It does **not** wire the SWA login flow or touch the D22 gate (that's 3.3). Until 3.3, nobody can actually sign in to the deployed app yet — assignments just sit ready.

Roles available on `slaylist-auth-dev` (defined in Sprint 3.1):

| Role `value` | Who it's for | Fixed role ID |
|---|---|---|
| `uploader` | the kids' shared account — make/upload/play (includes listener rights) | `8f4b2d65-0c3e-4a97-b2c1-4d6e8f0a2b3c` |
| `admin` | your management/self-test account — library admin (D20, single-library) | `9a5c3e76-1d4f-4ba8-83d2-5e7f9a1b3c4d` |
| `listener` | play-only (not assigned this sprint) | `7e3a1c54-9b2d-4f86-a1b0-3c5d7e9f1a2b` |

**Prerequisites:** `az login` to the tenant that owns `slaylist-auth-dev`; directory permission to create users + assign app roles (**User Administrator** + **Application Administrator**, or a personal tenant where you're the owner).

---

## Step 1 — Create the two accounts (Entra cloud users)

These are **cloud-only member users**. They need **no license and no mailbox** — a user can sign in to the app without M365. You set a password; it's an Entra password (consistent with D2 — no *local app* passwords; identity is Entra).

**Portal:** Microsoft Entra ID → **Users** → **New user** → **Create new user**, twice:

| Field | Uploader (kids) account | Admin account |
|---|---|---|
| User principal name | `<family-uploader-account>@<your-tenant>.onmicrosoft.com` | `<admin-account>@<your-tenant>.onmicrosoft.com` |
| Display name | a non-identifying label of your choice (no kid's real name) | a non-identifying admin label of your choice |
| Password | auto-generate or set; **record in gitignored notes** (it's a shared credential) | same |
| Usage location / license | none needed | none needed |

> Tip: the kids' account is a **shared** login (one credential the kids use together). Per-kid private accounts are a deliberately deferred path (BACKLOG "Per-kid private spaces via guest-invite Entra accounts").

**`az` equivalent (optional):**
```
az ad user create --display-name "<label>" \
  --user-principal-name "<family-uploader-account>@<your-tenant>.onmicrosoft.com" \
  --password "<set-a-strong-password>" --force-change-password-next-sign-in false
```

## Step 2 — Assign the roles

> ⚠️ **These are *app roles*, not groups.** Assign them from the **enterprise application's** "Users and groups" blade (below) — **NOT** from the user's own **Groups** blade. The user's Groups blade only lists directory groups, so `uploader`/`admin` will never appear there (a common dead-end).

**Portal:** Microsoft Entra ID → **Enterprise applications** → **`slaylist-auth-dev`** → **Users and groups** → **Add user/group**:
- Select the **uploader** account → **Select a role** → **Uploader** → **Assign**.
- Repeat: select the **admin** account → role **Admin** → **Assign**.

(Recall from Sprint 3.1: "assignment required" is on, so only users assigned here can sign in.)

**`az` equivalent (optional)** — assign an app role to a user via Microsoft Graph:
```
APPID=$(az ad app list --display-name slaylist-auth-dev --query "[0].appId" -o tsv)
SPID=$(az ad sp show --id "$APPID" --query id -o tsv)
# Use USEROID, not UID: UID is a read-only variable in bash, so `UID=...` silently fails to set
# and the assignment is made against the wrong principal.
USEROID=$(az ad user show --id "<family-uploader-account>@<your-tenant>.onmicrosoft.com" --query id -o tsv)
az rest --method post \
  --url "https://graph.microsoft.com/v1.0/users/$USEROID/appRoleAssignments" \
  --body "{\"principalId\":\"$USEROID\",\"resourceId\":\"$SPID\",\"appRoleId\":\"8f4b2d65-0c3e-4a97-b2c1-4d6e8f0a2b3c\"}"
```
(Use the `admin` role ID `9a5c3e76-1d4f-4ba8-83d2-5e7f9a1b3c4d` for the admin account.)

## Step 3 — Verify

**Portal:** Enterprise applications → `slaylist-auth-dev` → **Users and groups** shows both accounts with their roles.

**`az`:**
```
az rest --method get \
  --url "https://graph.microsoft.com/v1.0/servicePrincipals(appId='$APPID')/appRoleAssignedTo" \
  --query "value[].{user:principalDisplayName, roleId:appRoleId}" -o table
```
Expect two rows: the uploader account → `8f4b2d65…`, the admin account → `9a5c3e76…`.

## How to delete / reassign later

- **Reassign a role:** Enterprise applications → `slaylist-auth-dev` → Users and groups → select the assignment → **Remove**, then **Add user/group** again with the new role. (An app role is fixed per assignment; changing it = remove + re-add.)
- **Remove access entirely:** remove the assignment (above). The account still exists but can no longer sign in (assignment required).
- **Delete the account:** Microsoft Entra ID → Users → select → **Delete** (soft-deleted ~30 days, restorable). Deleting the user also drops its assignments.
- **Add a real per-kid account later:** create another user, assign it `uploader` (or `listener`), and retire the shared one — the deferred per-kid path, no code change needed.

## Capture + attest

Record in gitignored `infra/dev-resources.md` (the "Family accounts + role assignments" section of the template): each account's UPN, its role, and where the shared password is stored — **never in a committed file**. Attest: both assignments present (verified via Step 3); delete/reassign procedure understood.
