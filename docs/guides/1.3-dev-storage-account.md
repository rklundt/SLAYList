# Guide — Sprint 1.3: Dev Storage Account (blobs + table)

Human-executed walkthrough for Sprint 1.3. The pre-work has already been done (Storage Account template section in `infra/dev-resources.md.example`, BACKLOG retention-window question resolved, this guide written). You do the Azure portal side.

**Goal:** A dev storage account exists holding three blob containers (`raw-uploads`, `finished`, `table-backups`) and a `Songs` table, configured for soft-delete + versioning at a 30-day window, with **zero deletion-class lifecycle rules on `raw-uploads` (D28 hard guardrail)**, diagnostic settings forwarding to the LAW from Sprint 1.1, and the connection string captured locally as the secret Sprint 2.1 will promote to a GitHub Actions secret. Roughly **15–20 minutes**. Cost: $0–pennies (Standard LRS, near-zero data, free tier covers Tables operations).

---

## Critical principles (read before clicking anything)

Three invariants the configuration must satisfy. If a UI option contradicts one of these, STOP and report back — don't improvise.

1. **D28 — `raw-uploads` is the canonical archive.** Originals never get deleted. Soft-delete + versioning on. **NO deletion-class lifecycle rule, ever.** Tier-transition rules (Hot→Cool→Archive) are fine if added later for cost. Deletion-class rules are forbidden, full stop.
2. **D25 — Auth posture is split.** The connection string captured at this sprint is used **only by the SWA managed-functions API** (Sprint 2.1 + 2.2 propagate it). The Container App transcoder (Sprint 1.4 + Epic 6) authenticates via Managed Identity + RBAC roles instead, NOT this connection string. Both auth paths read the same data; the difference is platform-forced (managed functions can't use MI).
3. **D17 — public-repo hygiene.** The connection string is a real secret. It lives in **gitignored `infra/dev-resources.md` only** at this sprint, and (at Sprint 2.1) in GitHub Actions secrets. Never in any committed file, never in chat history that ends up on the public repo, never on any screenshot that gets shared.

## Step 3 — Create the storage account

1. Portal search → **Storage accounts** → **+ Create**.

2. **Basics tab — fill in:**

| Field | Value |
|---|---|
| **Subscription** | `Pay-As-You-Go` |
| **Resource group** | `rg-music-slaylist-dev-use2` ← *placement check* |
| **Storage account name** | `stmusicslaylistdevuse2` |
| **Region** | **East US 2** |
| **Performance** | **Standard** *(not Premium)* |
| **Redundancy** | **Locally-redundant storage (LRS)** *(cheapest; non-canonical data on dev per D7; prod 9.1 re-evaluates)* |
| **Make read access to data available in the event of unavailability** | leave unchecked *(only applies to GRS/RA-GRS)* |

   **If the name `stmusicslaylistdevuse2` is "already taken" globally**: that's a global-uniqueness collision. Fallback candidates in order: `stslaylistdevuse2` (17 chars) → `stmusicslaylistdev` (18 chars) → `stslaylistdev` (13 chars). All within Azure's 3–24 char limit, all hyphenless and lowercase. Pick the first available. Report back which one was used so the notes file matches reality.

3. **Advanced tab — confirm these settings (most are defaults; verify rather than skip):**

| Field | Value |
|---|---|
| Require secure transfer (HTTPS) | **on** *(default)* |
| Allow enabling anonymous access on individual containers | **off** *(default in new accounts; we keep it off — D25 + D17)* |
| Enable storage account key access | **on** *(default; the connection-string secret depends on this)* |
| Enable hierarchical namespace (Data Lake Gen2) | **off** *(important — turning this on changes blob semantics)* |
| Default to Microsoft Entra authorization in the Azure portal | leave default *(doesn't affect API auth; only the portal blob-viewer)* |
| Enable SFTP | **off** |
| Enable NFS v3 | **off** |
| Allow cross-tenant replication | **off** |
| Access tier (default tier for new blobs) | **Hot** |

4. **Networking tab — confirm:**

| Field | Value |
|---|---|
| Network access | **Enable public access from all networks** |
| Routing preference | **Microsoft network routing** *(default — lowest latency)* |

   **Why public network access stays enabled** (in case the portal nudges you toward restrictions): SWA managed functions can't use Private Endpoints (platform-forced, same constraint D25 documents for Managed Identity). Locking the storage account to private networking would break the Sprint 2.2 deploy path AND the local-dev path that connects through the connection string. The connection-string secret IS the access control. Same principle as D36 for App Insights.

5. **Data protection tab — this is where the soft-delete + versioning gets configured. Confirm:**

| Field | Value |
|---|---|
| **Enable soft delete for blobs** | **on**, **30 days** |
| **Enable soft delete for containers** | **on**, **30 days** |
| **Enable soft delete for file shares** | leave default (file shares unused) |
| **Enable versioning for blobs** | **on** |
| Enable blob change feed | leave **off** *(not needed for our use case; can be enabled later)* |
| Enable point-in-time restore | leave **off** *(versioning + soft-delete + table-backups is the recovery posture per D28/D33)* |

6. **Encryption tab** — leave defaults (Microsoft-managed keys; customer-managed keys are overkill at family scale).

7. **Tags tab** — same five tags as prior sprints:
   - `app=slaylist`
   - `env=dev`
   - `workload=music`
   - `managed-by=manual`
   - `cost-center=personal`

8. **Review + Create** → confirm everything (especially LRS, Standard, 30-day soft-deletes, versioning ON) → **Create**. Wait ~60–90 seconds for deployment.

## Step 6 — Verify D28 — zero deletion-class lifecycle rules on `raw-uploads`

This is the D28 hard guardrail. Verify, do not assume.

1. Storage account → left nav → **Lifecycle management** (under "Data management").
2. The list of rules should be **empty**. If empty: ✅ D28 holds for now (deletion-class rules would have to be deliberately added to violate it).
3. If the list is NOT empty (unlikely on a fresh account), inspect each rule's "Action" — if any action says *Delete blob*, *Delete previous version*, *Delete snapshot*, or similar AND its scope filter matches `raw-uploads`, **STOP and report back**. This shouldn't happen on a brand-new account, but verification is cheap.

**Future-you reminder**: never add a deletion-class lifecycle rule scoped to `raw-uploads`. Tier-transition rules (Hot → Cool → Archive) are allowed if storage cost ever becomes a real line item, but those are NOT deletion-class. The kids' originals stay forever.

## Troubleshooting

### "Storage account name `stmusicslaylistdevuse2` is already taken globally"

Azure storage account names are globally unique across all of Azure. Fallback in order:
1. `stslaylistdevuse2` (17 chars — drops the `<workload>` slot)
2. `stmusicslaylistdev` (18 chars — drops the region code)
3. `stslaylistdev` (13 chars — drops both)

Pick the first available. Report back the name used so the gitignored notes and any future references match reality.

### "Versioning grayed out / says 'not available for this redundancy'"

Versioning is supported on LRS Standard StorageV2 (our choice). If grayed out, double-check the account kind is StorageV2 (not Storage or BlockBlobStorage) and performance tier is Standard. Re-create if the choice was wrong.

### "Diagnostic settings says 'no Log Analytics workspace available'"

The workspace from Sprint 1.1 (`log-music-slaylist-dev-use2`) must be in the same subscription. Verify subscription = `Pay-As-You-Go` on both the storage account and the workspace.

### "I see SFTP / NFS prompts I didn't expect"

Newer portal versions sometimes ask about these on a separate tab. Both should be **off** for our use case (we use Blob API + Table API, not SFTP/NFS).

### "Public network access toggle keeps reverting"

Some org policies force `Enabled from selected networks` as a default. If you can't keep it at `Enabled from all networks`, you'll need to add SWA's egress IP ranges to the firewall — which Microsoft does not publish for SWA managed functions. Report back; we'll have to escalate or work around.
