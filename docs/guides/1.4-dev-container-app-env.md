# Guide — Sprint 1.4: Dev Container App Environment + placeholder Container App (with MI + storage RBAC)

Human-executed walkthrough for Sprint 1.4. The pre-work has already been done (Container App Environment + Container App template sections in `infra/dev-resources.md.example`, naming-convention row updated, this guide written). You do the Azure portal side.

**Goal:** A dev Container App Environment exists, AND a placeholder Container App in it with system-assigned Managed Identity granted `Storage Blob Data Contributor` + `Storage Table Data Contributor` roles on the storage account from Sprint 1.3, AND scale-to-zero verified, AND no storage connection string anywhere on the Container App (D25 invariant). Roughly **15–20 minutes**. Cost: $0–pennies (Consumption profile; with scale-to-zero and no traffic, idle compute = $0).

---

## Critical principles (read before clicking anything)

Three invariants the configuration must satisfy. If a UI option contradicts one of these, STOP and report back.

1. **D25 — Auth posture is split, and this is its "cleaner half."** The Container App authenticates to the storage account via **Managed Identity + Entra RBAC**, NEVER via a connection string or account key. The connection string captured at Sprint 1.3 is used only by the SWA managed-functions API (where MI isn't available — platform-forced). The Container App is forbidden from ever seeing the connection string. Portal Step B8 below explicitly verifies absence.

2. **D4 — Scale-to-zero is load-bearing.** Container App must be configured `min replicas = 0`. With no traffic and no KEDA scaling rule yet (those land at Sprint 7.x), the app sits at zero replicas = $0 idle compute. Without scale-to-zero we'd pay for always-on compute, which D4 rejected vs. App Service for exactly this reason.

3. **D22 N/A here, by design.** The transcoder Container App has **Ingress: Disabled** — it's back-end, triggered by queue messages (Epic 7), not by HTTP requests. No public endpoint = no anonymous-reachability risk = D22 doesn't apply. (Confirmed by Sprint 6.0's note: *"transcoder is back-end, not user-facing — D22 applies to user-facing environments."*)

**Portal display quirk to be aware of:** the GUID column on the storage account IAM Role assignments page displays the managed identity's **Application (Client) ID**, NOT the **Principal (Object) ID** that RBAC actually uses internally. For example, your Container App's Identity blade may show Object ID `aaaaaaaa-1111-...` while the storage IAM page shows GUID `bbbbbbbb-2222-...` — both identify the same Entra service principal. Different surfaces, different IDs displayed, same underlying identity. When debugging a runtime 403 in the future, cross-check via:
- Container App → Identity → Object (principal) ID
- Storage account → IAM → "Check access" tool, enter the Principal ID, confirm the two storage data roles appear

This caused brief confusion at the initial Sprint 1.4 Phase B (the GUIDs didn't appear to match → looked like an orphaned-MI bug → turned out to be the display-quirk above). No action needed beyond awareness.

## Troubleshooting

### "Container App Environments creation hangs or times out"

Environments take longer to provision than most Azure resources (2-5 min typical, sometimes longer if the platform is busy). Wait. If it fails outright, check **Activity log** on the RG for the specific error — often it's a regional capacity issue (rare) or a missing provider registration (rare on a sub that's already created Container Apps).

### "I don't see Container App as an option in 'Assign access to → Managed identity → Container App'"

The Managed Identity dropdown is populated only after the Container App's MI has been enabled and a brief propagation delay (~30 sec). If you just enabled MI in Step 5, wait a minute and refresh. If still not showing, verify Step 5 actually saved (refresh Identity blade — Status should still be On).

### "Storage Blob Data Contributor vs Storage Blob Contributor — which one?"

**Data Contributor** = data plane (read/write/delete actual blob contents). This is what we need.
**Contributor** = control plane (manage the blob service configuration, lifecycle rules, etc.). This is NOT what we need; would over-grant.

If you accidentally pick Contributor, remove it and re-add Data Contributor.

### "Replica count stays at 1 indefinitely despite no traffic"

**This is actually expected for Sprint 1.4's state — not a bug.** Container Apps' scale-to-zero behavior requires a *trigger signal* to know "drop to 0 now." Without either of:
- HTTP traffic on the ingress endpoint (we have **Ingress: Disabled** for the back-end transcoder)
- A KEDA scale rule firing "0 events → 0 replicas" (lands at **Sprint 7.x** with the queue trigger)

…the platform keeps the warm replica around for a long platform-internal cooldown window. The Sprint 1.4 acceptance "scale-to-zero capability confirmed" is satisfied by **configuration** (min=0, max=1, no force-min scale rule); observed runtime 0 comes either when Sprint 7.x wires the queue trigger OR when the platform's idle cooldown elapses (variable, can be 30+ min).

**Cost while warm:** ~$0–$2/mo at the configured 0.25 CPU / 0.5 GiB (Container Apps' free monthly grant of 180,000 vCPU-seconds + 360,000 GiB-seconds typically covers a single small idle replica). The $5 budget alert (Sprint 1.1) catches any runaway.

**If you want to force $0 cost during the Sprint 1.4 → 7.x gap:** Container App → Overview → **Stop** button. Reactivate at Sprint 6.x when image work begins.

### "I see an env var or secret on the Container App that I didn't add"

Some Azure-injected env vars (e.g., `CONTAINER_APP_NAME`, `CONTAINER_APP_REVISION`) are automatic and not D25 violations. The forbidden shapes are specifically: anything matching `*CONNECTION_STRING*`, `*ConnectionString*`, `AzureWebJobsStorage`, `*AccountKey=*`. If you see anything matching those, STOP and report back.
