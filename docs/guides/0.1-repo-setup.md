## Step 1 — Confirm prerequisites locally

In a terminal, in your project directory (the local path where you cloned this repo — must be on a filesystem with symlink support per D34: NTFS on Windows, ext4/APFS elsewhere; exFAT/FAT32 break `pnpm install`):

```powershell

# Confirm gh (GitHub CLI) is installed — you'll use it for auth

# Confirm you're authenticated to GitHub as the right account

```

If `gh auth status` shows you are not logged in or shows the wrong account, run:

```powershell

```

Choose: GitHub.com → HTTPS → authenticate with a browser. Confirm the account that owns this repo is the one logged in.

## Step 8 — Branch protection on `main` (and `develop`)

Easiest via the web UI: **Settings → Branches → Add branch ruleset** (or "Add classic branch protection rule" — either works for our purposes).

For **`main`**:

- Branch name pattern: `main`
- ✅ Require a pull request before merging
- ✅ Require approvals: 1 (or 0 if you're the only reviewer — but keep "require PR" on)
- ✅ Require linear history (recommended — keeps PR history readable)
- ✅ Restrict who can push to matching branches → only you / admins
- ✅ Do not allow bypassing the above settings (or, on a solo repo, allow yourself to bypass deliberately for the rare emergency, but think hard before doing so)

For **`develop`** (lighter, but on):

- Branch name pattern: `develop`
- ✅ Require a pull request before merging (keeps the sprint loop honest)
- Approvals: 0 is fine for now (you're the only reviewer).

`gh` equivalent (optional, repeat for each branch):

```powershell
gh api -X PUT repos/:owner/:repo/branches/main/protection -f required_pull_request_reviews.required_approving_review_count=1 -F required_linear_history=true -F enforce_admins=false -F restrictions=null
```

If the `gh api` form errors, just use the UI — branch protection settings are fiddly to script and the UI is faster on a one-time setup.

## Step 8b — Enable public-repo security baseline (D31)

While in **Settings**, enable the free-on-public-repos security features. Each is a one-click toggle.

- **Settings → Code security**:
  - ✅ **Secret scanning** — alerts on committed secrets.
  - ✅ **Push protection** — *blocks* secrets at `git push` time. This is the critical control: it prevents the permanent-history nightmare that `git filter-repo` only partially fixes on a public repo (mirrors, forks, search indexers may already have the secret).
  - ✅ **Dependabot alerts** + ✅ **Dependabot security updates** — auto-PRs for vulnerable dependencies.
  - ✅ **CodeQL analysis** (default setup is fine) — SAST for TypeScript.

`gh` equivalents (per feature; some require an additional CLI extension — UI is fine):

```powershell
gh api -X PATCH repos/:owner/:repo -F security_and_analysis[secret_scanning][status]=enabled -F security_and_analysis[secret_scanning_push_protection][status]=enabled
```

If any command errors, use the UI — the toggles are clearly labeled.

## Step 8c — Post-push secret-scanning verification (IS-4)

Immediately after the first push and after enabling the security baseline above, confirm GitHub agrees nothing sensitive was committed. **Note:** `gh secret-scanning` is **not** a built-in subcommand on the current `gh` CLI; use the REST API directly:

```powershell
gh api repos/rklundt/SLAYList/secret-scanning/alerts --jq '. | length'
gh api repos/rklundt/SLAYList/dependabot/alerts --jq '. | length'
```

Expected: both return `0` (no open alerts).

Or visit the Security tab in the GitHub UI: <https://github.com/rklundt/SLAYList/security>.

If anything is flagged: **treat the secret as already-leaked** (it's public the moment it hit GitHub, even if you delete it next). Rotate the actual value (the storage key, the token, whatever it was), then remove from history per the "If something goes wrong" section below. Do not assume "I'll just delete the file" — the secret is in the commit object and in any clone/mirror anyone made in the intervening seconds.

## If something goes wrong

- **You accidentally pushed something sensitive before catching it.** Treat the value as compromised — rotate any leaked secret, rename any leaked resource — and remove the file in a follow-up commit. `git history` is permanent on a public repo; rewriting history (`git filter-repo`) on something that's been public for any window is not a clean solution. Prevention beats cleanup; the hygiene scan in Step 2 is why.
- **You picked the wrong repo name.** `gh repo rename <new-name>` works after the fact; update the remote URL with `git remote set-url origin <new-url>`.
- **You created it private by mistake.** `gh repo edit --visibility public --accept-visibility-change-consequences` flips it. Re-verify the hygiene scan first — if the repo was private even briefly, you may have committed something assuming privacy.
