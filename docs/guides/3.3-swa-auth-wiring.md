# Wire client-side MSAL login — operator guide (Sprint 3.3)

This is the sprint where **login goes live** on the deployed dev app. Most of 3.3 is committed code
(Phase A — the MSAL SPA, the API's bearer-token validation, the deploy wiring). Your part (Phase B)
is the Entra app changes that make MSAL work — a **SPA redirect URI** and an **exposed API scope** —
plus a live sign-in check.

> **Why this changed from the original plan.** Custom SWA authentication (a custom Entra `auth` block
> in `staticwebapp.config.json`) is **Standard-SKU only**, and this family-only app stays on SWA
> **Free** (D26). So auth is **client-side MSAL** with the **API validating the bearer token** (D43),
> not an SWA edge gate. The static shell is public; every `/api/*` data request needs a valid,
> role-bearing token. D22's invariant holds — auth sits at the API now. SWA built-in auth on Standard
> stays the documented later switch, and the client secret + Web redirect are kept **dormant** on the
> registration so that switch stays a small change.

> **Hygiene (D17):** the client id + tenant id are public once in the SPA bundle (true of any OAuth
> SPA) — but still kept out of source and injected at build from GitHub secrets. No secret value is
> handled in Phase B: MSAL is a public client (PKCE), so **no client secret** is used today.

## Step 1 — add the SPA redirect URI + exposed API scope (scripted)

From the repo root (PowerShell), run the extended bootstrap script. It adds the SPA redirect URIs
(the dev SWA origin + `http://localhost:5193`) and exposes the `access_as_user` API scope. Steps 1–4
re-assert idempotently; step 7 (client secret) is **dormant** — it won't create another if one exists.

```
powershell -ExecutionPolicy Bypass -File .\scripts\bootstrap-auth-app.ps1
```

- `-DryRun` first to preview (nothing is created).
- Run `-RunUpToStep 6` if you want to stop before the (dormant) client-secret step; the full run also
  prints the verification summary (SPA URIs, App ID URI, exposed scope, role list).
- **Portal equivalents** (if you'd rather do it by hand), on `slaylist-auth-dev`:
  - *SPA redirect:* **Authentication** → Add a platform → **Single-page application** → add
    `https://<dev-swa-host>` and `http://localhost:5193`.
  - *API scope:* **Expose an API** → Set the Application ID URI to `api://<appId>` → Add a scope
    `access_as_user` (who can consent: **Admins and users**) → set the manifest
    `api.requestedAccessTokenVersion` to `2`.

## Step 2 — GitHub secrets (already set from the earlier run)

MSAL needs only the **public** ids. These were set during the first Phase B pass and need no change:

| GitHub `dev` env secret | Used by |
|---|---|
| `AAD_CLIENT_ID` | the SPA build (`VITE_AAD_CLIENT_ID`) + the API's token audience |
| `AZURE_TENANT_ID` | the SPA authority (`VITE_AAD_TENANT_ID`) + the API's issuer/JWKS |
| `AAD_CLIENT_SECRET` | **dormant** — kept for a future built-in-auth switch; **not** wired into SWA today |

Confirm with `gh secret list --env dev`. (No new secret is created in this sprint.)

## Step 3 — deploy

The config + workflow are on the sprint branch. On merge to `develop` (or `workflow_dispatch`), the
pipeline: bakes `VITE_AAD_CLIENT_ID`/`VITE_AAD_TENANT_ID` into the SPA bundle, wires
`AAD_CLIENT_ID`/`AAD_TENANT_ID` into SWA app settings (the API's validation inputs), and deploys.

## Step 4 — verify (the load-bearing check)

On the deployed dev URL:
- **The page loads without sign-in** (the shell is public now) and shows a **Sign in** button.
- **Sign in as an assigned account** (your uploader account → uploader, or the admin account → admin). MSAL redirects to
  **your** Entra app. On first sign-in you may be asked to **consent** to *"Access the SLAYList API"* —
  that's the exposed scope (an admin can pre-consent for everyone in Entra → Enterprise applications →
  `slaylist-auth-dev` → Permissions → Grant admin consent).
- **The app shows your role** (`uploader` / `admin`) — it read `GET /api/me` with the bearer token.
  If the role comes back `none`/`error`, the `roles` claim isn't reaching the API: check the role
  assignment (Sprint 3.2) and that the token audience matches `AAD_CLIENT_ID`. Stop and flag.
- **An un-logged-in `GET /api/me` returns 401** (the function rejects a missing/invalid token).
- **A non-assigned Microsoft account cannot complete sign-in** (Entra blocks it via
  `appRoleAssignmentRequired`) — the any-Microsoft-account gap from Epic 2 stays closed.

## The future switch (for reference)

If the app is ever rolled out more widely, SWA built-in auth on **Standard** becomes worth it. The
groundwork is already here: the Web redirect + client secret are registered (dormant), and the API's
`getCaller()` is the only code that changes (swap bearer-JWT validation for the SWA
`x-ms-client-principal` header). See D43 for the full migration surface.
