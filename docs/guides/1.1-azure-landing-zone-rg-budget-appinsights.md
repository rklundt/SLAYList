## Step 4 — Create Application Insights

1. Portal search → **"Application Insights"** → **+ Create**.
2. **Subscription:** pay-as-you-go
3. **Resource group:** `rg-music-slaylist-dev-use2` *(verify — placement check)*
4. **Name:** `appi-music-slaylist-dev-use2`
5. **Region:** **East US 2**
6. **Resource Mode:** **Workspace-based** (should be default; classic is greyed out / unavailable for new resources)
7. **Log Analytics workspace:** select `log-music-slaylist-dev-use2` from the dropdown *(this is what makes it workspace-based — verify it's set)*
8. **Tags** (Next → Tags): same five tags.
9. Review + Create → Create. Wait ~30 seconds.

10. Once deployed, click **Go to resource**.
11. On the **Overview** page, you'll see the **Connection String** (full string starting with `InstrumentationKey=...;IngestionEndpoint=https://eastus2-...`) and the **Instrumentation Key** (a GUID — legacy, but still shown).
12. **Configure retention:** for workspace-based App Insights (our case), retention is **set on the linked Log Analytics workspace, NOT on App Insights** (Microsoft removed the AI-level "Data Retention" control when AI moved to workspace-based — only daily cap + sampling % remain on AI). To set it: navigate to `log-music-slaylist-dev-use2` → Settings → **Usage and estimated costs** → **Data Retention** (button at top of the blade). The LAW default is **30 days** — sufficient for family-scale failure forensics. Extending to 90 days is free at our volume but not required for dev; revisit for prod at Sprint 9.1 once real traffic exists.

    **Two-knob warning for Sprint 9.1 prod retention work:** LAW exposes two distinct retention settings — **Interactive Data Retention** (queryable hot data; the one most operators mean by "retention" and the one most reviewer/cost discussions reference) and optional **Total Retention** (cold archive past the interactive window; cheaper-per-GB but not queryable in the normal Logs blade — needs `archive`-aware queries). Sprint 1.1 leaves both at the LAW defaults. When prod retention gets configured at 9.1, set the **Interactive** knob to the chosen value first; only touch Total Retention if there's an explicit archive-for-compliance need (no such need at family scale).

13. **Set the Daily Cap (defense-in-depth against iKey-leak abuse):** App Insights → Usage and estimated costs → **Daily Cap** → set to **1 GB/day** → Save. Default is 100 GB/day which is effectively unbounded at family scale; if an iKey ever leaks and someone spams telemetry, ingestion stops at ~$2.30/day worth instead of ~$230/day worth — bounding the incident automatically without relying on owner-reaction-time to the $5 budget alert. Free to set; no cost downside at our volume (steady state is well under 1 GB/month). Sprint 9.1 prod sets the same cap, possibly higher (~5 GB/day) once real traffic exists.
13. **Capture** in `dev-resources.md` → "Application Insights" section:
    - Connection string (the full one)
    - Instrumentation key
    - Resource ID (from Overview → JSON View)
    - Retention confirmed at 90 days

**SECURITY CHECK:** the connection string IS a secret (it grants telemetry-write to your App Insights). It lives in your gitignored `dev-resources.md` for reference; in Sprint 2.1 it gets stored as a GitHub Actions secret named `APP_INSIGHTS_CONNECTION_STRING_DEV`. Never paste it into a committed file, a chat where it might be logged, or a screenshot.

## Step 5 — Verify telemetry ingestion (so you know the sink works BEFORE any real code exists)

The DevOps reviewer line says "App Insights ingestion verified (a test event from any source lands and is queryable)." This is the cheapest, earliest sanity check that the sink is alive.

**Option A — easiest, no CLI:** use the portal's built-in test ping.

1. On the App Insights resource → left nav → **Availability**.
2. **+ Add Classic Test** (or "URL ping test") → just create a simple URL ping to `https://www.microsoft.com` (any reliable URL) with a 5-minute frequency, **named** `smoke-test-1.1` (you'll delete it in 10 minutes).
3. Wait 5 minutes.
4. Left nav → **Logs**. Run:
   ```kql
   availabilityResults
   | where timestamp > ago(1h)
   | take 10
   ```
   You should see at least one row from the `smoke-test-1.1` ping.
5. **Confirm ingestion verified.** Delete the test (back on **Availability**, select `smoke-test-1.1`, **Delete**) — its only job was the smoke test.

**Option B — direct POST to the ingestion endpoint (recommended over Option A; ~3 min total):**

This is the most authentic smoke test — it exercises the exact ingestion path our deployed code will use, the connection string IS the credential (no `az` login juggling needed), and the event lands in `customEvents` within 1-3 minutes.

In PowerShell, substitute `<your-ingestion-endpoint>` and `<your-ikey>` from the connection string you just captured in `infra/dev-resources.md` (the ingestion endpoint is the value after `IngestionEndpoint=`, ending in `/v2/track`; the iKey is the value after `InstrumentationKey=`):

```powershell
$endpoint = "<your-ingestion-endpoint>v2/track"   # the value of IngestionEndpoint= in your connection string (ends in "/") + "v2/track"
$iKey = "<your-ikey>"                               # the value of InstrumentationKey= in your connection string (a GUID)
$envelope = @{
    name = "Microsoft.ApplicationInsights.Event"
    time = (Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ss.fffZ")
    iKey = $iKey
    tags = @{ "ai.cloud.role" = "smoke-test-1.1" }
    data = @{
        baseType = "EventData"
        baseData = @{
            ver = 2
            name = "smoke-test-1.1"
            properties = @{ source = "manual-verification"; sprint = "1.1" }
        }
    }
} | ConvertTo-Json -Depth 6
Invoke-RestMethod -Uri $endpoint -Method Post -Body $envelope -ContentType "application/json"
```

**Expected output:** `itemsReceived: 1`, `itemsAccepted: 1`, `errors: {}` (empty). Wait 1-3 min for ingestion lag, then in the portal:

`appi-music-slaylist-dev-use2` → left nav → **Logs** → run:

```kql
customEvents
| where timestamp > ago(15m)
| where name == "smoke-test-1.1"
| project timestamp, name, cloud_RoleName, customDimensions
```

You should see exactly one row.

**Why not `az monitor app-insights events show`?** That command only *reads* events, and a brand-new AI resource has none — so it would return empty for the wrong reason. The POST approach above proves the actual write path, which is what we care about.

**For Sprint 9.1 (prod equivalent):** substitute the prod ingestion endpoint and iKey from `prod-resources.md`. Change the role/event-name to `smoke-test-9.1` so the test event is unambiguous.

**Either way:** confirm in your local notes "ingestion verified on <date>" — this becomes a /wrap-sprint review checkpoint.

## Step 6 — Create the $15/month RG-scoped budget

1. Portal search → **"Cost Management + Billing"** → in the left nav of the page that opens, **Cost Management** → **Budgets**.
2. **Scope** (top of page): click **Change scope** → select the resource group `rg-music-slaylist-dev-use2`. *(Critical — if this shows "Subscription / Pay-As-You-Go" instead of the RG, the budget will measure the wrong total.)*
3. **+ Add**.
4. **Name:** `budget-music-slaylist-dev`
5. **Reset period:** Monthly
6. **Creation date:** today
7. **Expiration date:** leave at default (typically 5 years out — Azure caps budgets)
8. **Amount:** `15`
9. **Next** → **Alert conditions**:
   - **Rung 1:** Type = Actual, Threshold = `33`%, → $5.00, **Action group = None** — comment line: "early warning ($5; family-scale steady-state is $0-2/mo; anything above $5 is already abnormal)"
   - **Rung 2:** Type = Actual, Threshold = `80`%, → $12.00, **Action group = None** — "warning"
   - **Rung 3:** Type = Actual, Threshold = `100`%, → $15.00, **Action group = None** — "action-needed"

   **About the "Action group" dropdown:** Azure auto-creates an action group named **"Application Insights Smart Detection"** when you create App Insights at Step 4 — it appears in this dropdown. **Do NOT select it for budget alerts.** Two reasons: (a) semantic mismatch (it's named for AI anomaly events, not budget alerts — confusing six months later); (b) duplicate-notification risk (you'll already get email via the recipients field below; the Smart Detection group fires a second notification through its own configured path). Select **None** for all three rungs; the simple email path below is enough at family scale. A purpose-named action group (e.g. `ag-slaylist-<env>-alerts`) becomes worthwhile when the BACKLOG "Dedicated alerts mailbox" change lands, coordinating budget + AI smart-detection + future deploy-failure alerts through one recipient list — not Sprint 1.1 work.

10. **Alert recipients (email):** the address recorded in your local `infra/dev-resources.md` "Notification email" field. (Not committed here per public-repo hygiene — personal email addresses don't land in public source. See the BACKLOG entry "Dedicated alerts mailbox" for the future-state improvement.)
11. **Language:** English
12. Create.

13. **Capture** in `dev-resources.md` → "Budget alerts" section: confirm all three rungs are listed.

**If the portal asks about "Forecasted vs Actual":** use **Actual** for all three rungs. Forecasted alerts are projections that often fire on day 1 of a month from a single spike; Actual fires on what you've genuinely spent. For a $0–2/mo baseline app, Actual is the right signal.

## Troubleshooting

### "I don't see the pay-as-you-go subscription in the directory I'm in"
The subscription is bound to a tenant. If you're in the wrong tenant, the sub won't appear. Re-check Step 1 — switch to the personal-MSA tenant.

### "The Log Analytics workspace creation says my subscription isn't registered for Microsoft.OperationalInsights"
First-time resource-type use on a fresh sub sometimes requires explicit provider registration. Run in Azure CLI:
```powershell
az provider register --namespace Microsoft.OperationalInsights
az provider register --namespace Microsoft.Insights
```
Wait ~60 seconds, retry. Or use the portal: Subscription → Resource providers → search the provider → Register.

### "App Insights workspace dropdown is empty"
The workspace you just created in Step 3 takes ~60 seconds to be queryable by the App Insights creation flow. Wait a minute and refresh the page.

### "Budget creation says 'no scope selected' or scope is greyed out"
Make sure you used **Change scope** *at the top of the Budgets page* before clicking **+ Add**. The scope is set page-wide, not per-budget.

### "The connection string I see is shorter than the example"
Older App Insights resources (pre-2022) had simpler instrumentation-key-only connection strings. Workspace-based App Insights created in 2023+ should always have the full `InstrumentationKey=...;IngestionEndpoint=...;LiveEndpoint=...;ApplicationId=...` form. If yours is shorter, you may have accidentally created a classic-mode resource — recreate as workspace-based.
